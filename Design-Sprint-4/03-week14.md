**What to take from Kholmatova:** the useful distinction is not atoms versus molecules, it is *functional* patterns (what a thing does) versus *perceptual* patterns (how a thing feels). Two components that look different but do the same job are a duplication problem. Two that look the same but do different jobs are a naming problem.

→ **Commit** `students/UX{n}/week14/session1-learning.md`

## DO — 2.5 hours

### T2.1 — Inventory and API design

**Method**
1. Pick six components to own this sprint. At least one must be complex — a data table, a combobox, a date picker, or a multi-select.
2. For each, design the **API before you draw anything**:
   - **Variants** — what fundamentally different versions exist
   - **Sizes** — how many, and why that many
   - **States** — the full set
   - **Slots** — where a consumer can put arbitrary content
   - **Props** — every configurable option, with its default
3. For every property, answer: why does this exist, what happens if it is absent, and what does it prevent someone from doing?
4. **Then write what the component does not do**, and where that responsibility lives instead. This section prevents scope creep, and it is the part that gets skipped.

**Worked example** — a button API:

> **Variants:** primary, secondary, tertiary, destructive. Four, because those are the four hierarchies a screen needs. Not "ghost" and "outline" as separate things — those are the same hierarchy with different perceptual treatment, and having both invites inconsistency.
> **Sizes:** small (32px), medium (40px), large (48px). Three. Small exists for dense table rows in the doctor console. Large exists for the patient app's primary CTA. Medium is everything else and is the default.
> **States:** default, hover, focus-visible, active, loading, disabled.
> **Slots:** leading icon, trailing icon. Label is a prop, not a slot, deliberately — a slot would let someone put a whole layout inside a button.
> **Props:** `variant` (default: secondary), `size` (default: medium), `fullWidth` (default: false), `loading` (default: false), `disabled` (default: false), `iconLeading`, `iconTrailing`.
>
> **Why `variant` defaults to secondary and not primary:** a screen should have one primary action. If primary is the default, every button someone drops in is primary and the hierarchy is gone by the third one. The default should be the safe choice, not the loud one.
>
> **What this does not do:** it is not a link. It does not handle navigation semantics, it does not support an `href`. A visual button that navigates is a Link component with button styling, because the semantic element must match the behaviour — `<a>` for navigation, `<button>` for actions. Keyboard behaviour differs (Enter versus Space) and screen readers announce them differently.

**Done when**
- [ ] Six components chosen, at least one complex
- [ ] Every API designed before any drawing
- [ ] Every property justified, with its default stated
- [ ] Every default choice explained, not just declared
- [ ] Every component has a "what this does not do" section naming where the responsibility goes instead

## DO — 3 hours

### T2.2 — Build three components

**Method**
1. Build three of your six in Figma. Full variant sets, using Figma component properties, consuming the T1 tokens.
2. Zero hard-coded values. Every colour, space, radius, and duration comes from a token.
3. Every state built, including loading and disabled.
4. **Test each one at 200% zoom and in the narrowest viewport you support.** Components break at the edges, and the edges are where users with low vision live.

**Done when**
- [ ] Three components complete with all variants and states
- [ ] No hard-coded values anywhere
- [ ] Figma component properties used, not manual variant swapping
- [ ] Tested at 200% and at the narrowest viewport
- [ ] Both themes verified

# Day 3

## LEARN — 60 minutes

| Source | What exactly | Time |
|---|---|---|
| **Design Systems** | The chapter on composition and on system flexibility | 30 min |
| **Any headless UI library docs** | Radix, React Aria, or Headless UI — read how they expose composition and slots | 30 min |

**Why headless libraries:** they separate behaviour from appearance, which is the same separation you are making between API and visual design. Their APIs are the most carefully designed component APIs in public, because they cannot fall back on visual defaults.

→ **Commit** `session3-learning.md`

## DO — 3 hours

### T2.3 — Build three more, with slots

**Method**
1. Build the remaining three, including your complex one.
2. Use slots where content is genuinely arbitrary.
3. **For every slot, state what is allowed in it and what is not.** An unconstrained slot is how systems die: someone puts a form inside a table cell, and now your component is responsible for a layout you never designed.
4. Document what happens when a slot receives too much content, and what happens when it receives nothing.

**Worked example** — a card component's slot constraints:

> **Slot: `media`.** Allowed: a single image or video, aspect ratio 16:9 or 1:1. Not allowed: arbitrary content, multiple images, or a carousel. If you need a carousel, the card contains a Carousel component and the card does not manage it.
> **Empty behaviour:** the media area is removed entirely, not collapsed to a placeholder. The card reflows.
> **Overflow behaviour:** the image is cropped to the aspect ratio with `object-fit: cover`, anchored to the centre. There is no configuration for the anchor, deliberately — if you need art direction, the image is wrong for a card.

**Done when**
- [ ] Six components total, complete
- [ ] Every slot has stated allowed and disallowed content
- [ ] Empty and overflow behaviour documented per slot
- [ ] The complex component's full interaction model specified
- [ ] All tokens, no hard-coded values

# Day 4

## LEARN — 60 minutes

Read the documentation pages for three components you consider well documented, from any real system. Identify the exact sections they all have, and the order they come in. That is your template.

→ **Commit** `session4-learning.md`

## DO — 2.5 hours (plus critique)

### T2.4 — Documentation

**Method**
Every component gets a page with: what it is for · when to use it · **when not to use it, with what to use instead** · anatomy with named parts · every variant with its use case · every state · the full API table with types and defaults · keyboard interaction · screen reader announcement · the semantic element · content guidelines with real examples · one do and one do not, both showing real mistakes · related components.

Publish at least one component's page as a **Storybook** docs page (MDX or autodocs) so the documentation, the live component and every state sit in one place. The other components may stay in Markdown.

**The test:** a peer builds your component from the documentation alone, without speaking to you. Whatever they get wrong is a documentation bug, not their mistake. Fix it and record what was missing.

**Done when**
- [ ] All twelve sections for all six components
- [ ] "When not to use" names an alternative for each
- [ ] Do and do not examples show real mistakes, not strawmen
- [ ] Keyboard and screen reader behaviour specified per component
- [ ] At least one component documented in Storybook with all states reachable
- [ ] A peer has built one from the docs alone, and every gap is logged and fixed

→ `students/UX{n}/week14/T2-4-documentation/`

### T2.5 — Composition rules

**Method**
1. Document which components can contain which. A grid of container components against contained components.
2. **Document the combinations that must not exist**, and say why. A modal inside a modal. A form inside a table cell. A card inside a card.
3. For each forbidden combination, state what someone should do instead. A prohibition with no alternative gets ignored.

**Done when**
- [ ] A containment matrix covering all six components
- [ ] At least four forbidden combinations, each with a reason
- [ ] An alternative given for every prohibition
- [ ] Nesting depth limits stated where they matter

→ `students/UX{n}/week14/T2-5-composition.md`

### Critique — 90 minutes
Bring one component's documentation and nothing else. A peer attempts to build from it live. **You are not allowed to speak** during the attempt. Every question they need to ask is a documentation failure, and the count is the grade.

# Day 5

## LEARN — 60 minutes

Read the ARIA Authoring Practices Guide pattern for each of your six component types, in full, including the keyboard interaction tables.

→ **Commit** `session5-learning.md`

## DO — 2 hours

### T2.6 — Accessibility specification

**Method**
For each component: the semantic HTML element · the ARIA role if the native element is insufficient · every required attribute and its state changes · the full keyboard interaction table · the screen reader announcement in each state · the focus behaviour · the target size.

**First rule of ARIA applies.** If a native element does the job, use it and add nothing. `<button>` beats `<div role="button" tabindex="0">` on every axis, including the ones you have not thought of.

**Done when**
- [ ] Semantic element named for each, native wherever possible
- [ ] Keyboard interaction table complete for each, matching the APG
- [ ] Screen reader announcement written for every state
- [ ] Focus behaviour specified
- [ ] Target sizes meet 24×24 minimum, with 44×44 noted where it applies
- [ ] Any ARIA use justified by the absence of a native equivalent

→ `students/UX{n}/week14/T2-6-a11y-spec.md`
