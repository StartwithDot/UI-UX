→ **Commit** `students/UX{n}/week13/day1-learning.md`

## DO — 2.5 hours

### T1.1 — Primitive layer

**Method**
1. Build the raw values. Colour ramps, type sizes, spacing, radii, border widths, shadows, durations, easings.
2. Primitives are named for **what they are**, never for what they do. `blue-500`, `space-4`, `radius-md`, `duration-200`.
3. Colour: full ramps, 50 to 900, perceptually even, for every hue you need — a brand hue, a neutral, and one each for success, warning, error, and information.
4. Nothing in this layer references anything else. Primitives are the bottom.
5. **State what you are not doing.** No component references a primitive directly. Write that rule down here, because it is the rule everyone breaks.

**Worked example** — the naming rule tested:

> `blue-500` is a valid primitive name because it describes the value. If the brand changes to green, this token does not get renamed — it gets removed, and a `green-500` takes over the semantic slots it was filling.
>
> `primary-blue` is an invalid primitive name, because it mixes a role ("primary") with a value ("blue"). The moment primary becomes green, the name is a lie and every usage has to be found by hand.

**Done when**
- [ ] Every category covered: colour, type, space, radius, border, shadow, duration, easing
- [ ] Full ramps for every semantic hue, not just the brand
- [ ] Every name describes the value, not the use
- [ ] No primitive references another token
- [ ] The "no direct primitive use" rule is written down

→ `students/UX{n}/week13/T1-1-primitives.md`

## DO — 2.5 hours

### T1.2 — Semantic layer

**Method**
1. Every semantic token names a **role** and points at a primitive.
2. Cover: text (default, subdued, disabled, on-colour, link, error) · surface (default, raised, sunken, overlay, disabled) · border (default, subdued, focus, error) · interactive (default, hover, pressed, disabled, focus-ring) · status (success, warning, error, info, each with a text, surface, and border variant).
3. Every token must answer: what is this for, and when would I not use it?
4. **This is the layer components consume.** Components never touch primitives.
5. Verify that every text-on-surface pairing in your semantic set meets 4.5:1, and every border and focus ring meets 3:1. A semantic layer that permits a failing combination is a broken semantic layer.

**Worked example**

| Semantic token | Points at | Used for | Do not use for |
|---|---|---|---|
| `text-default` | `neutral-900` | Body copy, headings, labels | Text on a coloured surface — use `text-on-colour` |
| `text-subdued` | `neutral-600` | Hint text, captions, timestamps | Anything a user needs to read to complete a task. Measured at 4.6:1 on `surface-default`, which passes, but it reads as secondary and users skip it. |
| `border-focus` | `blue-600` | The focus ring, all components | Decorative borders. It must remain unique to focus or focus stops being recognisable. |

Note the third row: the constraint is not just contrast, it is meaning. A token whose visual language is borrowed elsewhere stops communicating.

**Done when**
- [ ] Every category has its full set of roles
- [ ] Every semantic token points at exactly one primitive
- [ ] Every token has a "used for" and a "do not use for"
- [ ] Every text-on-surface pair measured, all pass 4.5:1
- [ ] Focus and border tokens measured at 3:1
- [ ] No component in your system references a primitive

→ `students/UX{n}/week13/T1-2-semantic.md`

## DO — 2.5 hours

### T1.3 — Component layer and theming

**Method**
1. Component tokens are the third layer: `button-primary-background` points at `interactive-default`, which points at `blue-600`.
2. Only create a component token where the component genuinely needs to diverge. Otherwise it consumes the semantic token directly. **A component token for everything is not architecture, it is bureaucracy.**
3. Now theme. The three products need to differ:
   - The mobile app: brand colours, comfortable density
   - The ops tool: neutral, compact density, higher information capacity
   - The marketing site: brand colours, generous density, larger type
4. **Every difference must be achieved by swapping which primitive a semantic token points at, or by swapping a density scale.** If you find yourself redesigning a component to theme it, your architecture has failed and this is where you find out.
5. Log every place theming was not enough, and say what you would restructure.

**Worked example** — density handled properly:

> The ops tool needs a compact table row. The wrong solution is a second table component. The right solution is a density scale: `space-comfortable-*` and `space-compact-*` primitive sets, with the semantic `table-row-padding` pointing at one or the other depending on the theme. The component is unchanged; the theme selects the spacing set.
>
> Where this broke for me: the marketing site needs a button with a 32px radius, and my `radius-*` scale tops out at 12px. That is not a theming failure, it is a missing primitive — I added `radius-full`. The failure would have been overriding the radius inside the component.

**Done when**
- [ ] Component tokens exist only where divergence is real, and each is justified
- [ ] Three themes defined
- [ ] Density handled by a scale, not by duplicate components
- [ ] No component redesigned in order to theme it
- [ ] Every place theming was insufficient is logged with a proposed fix

## DO — 2 hours (plus critique)

### T1.4 — Naming audit

**Method**
1. Write your naming convention as a formal rule. `{category}-{role}-{variant}-{state}`, or whatever you have chosen. Then verify every token conforms.
2. Test each name against three questions:
   - Does it survive the value changing?
   - Can someone who has never seen your system guess what it does?
   - Is it distinguishable from every other token when read quickly in a list?
3. Find every token that fails and rename it.
4. Write down the names you rejected and why. This is what stops the next person re-litigating your decisions.

**Done when**
- [ ] The convention is stated as a formal pattern
- [ ] Every token conforms, or the exception is documented
- [ ] All three tests applied to every token
- [ ] Rejected alternatives recorded with reasons
- [ ] No two token names differ only by a word that means the same thing

→ `students/UX{n}/week13/T1-4-naming-audit.md`

### T1.5 — Dark mode

**Method**
1. Add a dark theme by re-pointing semantic tokens. If you have to touch a component, note it as an architecture failure.
2. **Dark mode is not inversion.** Pure black backgrounds with pure white text cause halation and are uncomfortable; elevated surfaces get lighter in dark mode rather than darker; and saturated colours need desaturating because they vibrate against dark backgrounds.
3. Re-measure every contrast pair. Passing in light mode tells you nothing about dark mode.
4. State what you had to change beyond re-pointing, and why.

**Done when**
- [ ] Dark theme by re-pointing only, or every exception logged
- [ ] Elevation logic inverted correctly
- [ ] Saturated colours adjusted, with the reason stated
- [ ] Every contrast pair re-measured in dark mode
- [ ] All pass 4.5:1 and 3:1 respectively

→ `students/UX{n}/week13/T1-5-dark-mode.md`

### Thursday critique — 90 minutes
Present your semantic layer and one theme. The critique focus: **name three tokens you would have to rename if the brand colour changed to green.** If the answer is more than zero, the semantic layer is not doing its job.

### T1.6 — Export

**Method**
1. Export the tokens as JSON, in a structure a build tool could consume. W3C format if you can.
2. All three themes plus dark mode in the export.
3. Commit the JSON. **A token set that exists only in Figma is not a token set** — it is a set of Figma variables, and nothing outside Figma can use it.
4. Write the README that tells an engineer how to consume it.

**Done when**
- [ ] Valid JSON, committed
- [ ] All themes present
- [ ] Structure is machine-consumable, not a flat list of hex codes
- [ ] README explains consumption in enough detail to try

### P13.1 — Architecture decision record

**Method**
Write the ADR for your token architecture: context, the options you considered, your decision, the reason with evidence, the consequences, and what would change your mind.

Include the thing people leave out: **what your architecture cannot do.** Every architecture has a case it handles badly. Name yours before someone else does.

**Worked example** — the limits section:

> **What this cannot do.** My architecture handles colour, spacing, and type well, and it handles density adequately. It does not handle per-component brand divergence — if the marketing site wants a genuinely different button *shape* rather than a different radius value, my system cannot express that through tokens and would need a component variant. I have accepted this because only one of three products has expressive needs, and I would rather have one documented variant than a token layer complex enough to express arbitrary shape.
>
> **What would change my mind:** a second product needing expressive divergence. At two, the variant approach stops scaling and I would move to a slot-based composition model instead.

**Done when**
- [ ] All six ADR sections
- [ ] Alternatives considered, with the reason for rejection
- [ ] The limits section names a real weakness
- [ ] "What would change my mind" has a concrete trigger, not a vague one
